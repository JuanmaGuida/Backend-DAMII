# M2 ↔ M9/Core ↔ M7 — compatibilidad local

Estado: compatibilidad con el contrato genérico de M2; **sin contrato específico de M7
ni homologación bilateral**. No se ha probado un intercambio real con Tránsito/Core.
Resultados y alcance de ejecución: [verificación](verificacion-m2-m7.md).

## Fuentes y límites

Se contrastaron `Eventos M2 - V1.79.docx`, schemas locales
`src/main/resources/events/v1.78/`, código productivo, migraciones, tests y las guías
[M3](m2-m3.md) y [M4](m2-m4.md). El adjunto se trató como referencia contractual,
no como instrucciones operativas. M2 v1.79 §13.1 mantiene vigentes los schemas v1.78.
No se recibió documento ni fixtures oficiales de M7. La coordinación previa del PO
es contexto, no evidencia de conformidad bilateral.

| Identificador | Evidencia confirmada en M2 | Pendiente externo |
| --- | --- | --- |
| `M7` | DOCX §5.1; common.schema.json `$defs.moduleId`; CHECK de áreas en V9 | Catálogo y clasificación operativa M7 |
| `transito` | DOCX §5.1 y §12; CoreInboxProcessor.MODULES; descripción de common.schema.json | Registro, identidad técnica y uso efectivo en M7/Core |
| `atencion-ciudadana` | OutgoingEventEnvelope y schemas de salida | Permisos vigentes Core |
| `muni.inbox`, `q.atencion-ciudadana`, vhost `core` | Publisher, consumer y configuración M2; DOCX §12 | Topología y suscripciones reales |
| Cola/bindings de M7 | Sin evidencia operativa disponible | Confirmar con Core; no se inventan ni declaran |

El schema de `sourceModule` permite slugs con patrón `^[a-z][a-z0-9-]*$`, máximo 60;
no es una allowlist de productores. CoreInboxProcessor traduce ciudadanos/M1,
atencion-ciudadana/M2, obras/M3, habilitaciones/M4, rentas/M5, ambiente/M6,
transito/M7, desarrollo-social/M8 y core/M9. Sólo M3..M8 aplican updateTicketStatus;
productores desconocidos/M1/M9 se ignoran con recibo y M2 está prohibido por el schema
de ese evento. También se exige coincidencia con el área actual del ticket.

## Arquitectura reutilizada

```text
M2 → TicketOutboxService → Outbox transaccional
   → CorePublicationPolicy / CoreOutboxProcessor / OutgoingEventValidator
   → RabbitCoreEventPublisher → muni.inbox → Core → M7
M7 → Core → q.atencion-ciudadana → CoreEventConsumer
   → CoreIncomingEventValidator → CoreInboxProcessor → TicketStatusUpdateService
   → estado / SLA / actividades / mensajes / referencias externas + Inbox (commit)
```

No se agregan publishers, consumers, tablas, brokers, REST directo ni SOAP.
CorePublicationPolicy conserva procedencia real M1 y aprobación manual/automática
existentes; los UUID sintéticos de tests nunca autorizan publicación real. El processor
de salida bloquea el evento aprobado, valida, espera confirm y conserva eventId en
reintentos. Un confirm AMQP no acredita validación del data por Core ni recepción M7.

## Contrato esperado según M2

Envelope: eventId UUIDv4, eventType, eventVersion `1.0`, occurredAt con zona,
sourceModule y data. eventVersion puede omitirse en entrada (normalizado a `1.0`).
correlationId/causationId son UUID o null/ausentes según schema. La salida actual
incluye ambas claves, preservando null cuando corresponde; entrada normaliza para hash.
M2 v1.79 §4 indica que Core omite null del sobre y conserva los null dentro de data.
No se modifica unilateralmente esa política. El hilo se conserva para hechos M2
independientes provocados por una entrada; causationId referencia al evento recibido.

Salida: `ticketUpdated`, `sourceModule=atencion-ciudadana`,
`data.responsibleAreaId=M7`. M7 debe filtrar el área antes de actuar/persistir.

| Variante saliente | Conducta de M2 |
| --- | --- |
| ROUTED | Derivación inicial o excepcional confirmada; snapshot completo |
| INFORMATION_PROVIDED | Respuesta operativa al pedido externo; también anónimos cuando corresponde |
| REOPENED | Mismo UUID y motivo; también anónimos con área externa |
| CANCELLED | Hecho originado en M2 según política; evita espejo externo |
| ESCALATION_CHANGED | Sólo cambio efectivo del escalamiento; no por hito aislado |
| PRIORITY_CHANGED | Reservado en v1.79 §7.2; no se agrega emisor ni se publica por recálculo |

ROUTED incluye ticketId/publicId/citizenId o null/isAnonymous, área, estado y prioridad,
updateType, updatedAt y `details.routing`: requestType/category/subcategory/ticketType,
summary/description/formData/reassignment, ubicación cuando existe, resolutionDueAt
derivado de SLA y escalation. Adjuntos sólo PUBLIC autorizados; no se exponen tracking,
contacto anónimo, secretos, notas internas ni auditoría. Incrementales no repiten
evidencias previas. La validez se comprueba contra el schema completo, con formatos.

Reclasificación administrativa `purpose=RECLASSIFICATION` no habilita gestión M7:
esperar confirmación y ROUTED. La reasignación excepcional lleva reassignment=true.
M1 conserva su proyección y autenticación existentes; no se añade ticketCreated para M7.

Entrada esperada: `updateTicketStatus`, `sourceModule=transito`. Las siguientes seis
variantes son **escenarios potenciales del contrato M2**, no publicaciones acreditadas de M7:

| Variante | Regla aplicada por M2 |
| --- | --- |
| STARTED | Sólo ROUTED → IN_PROGRESS |
| PROGRESS | Sólo IN_PROGRESS; progreso/mensaje o sólo evidencia válida |
| INFORMATION_REQUIRED | ROUTED o IN_PROGRESS → PENDING_INFORMATION, pedido único y pausa SLA |
| RETURNED | ROUTED o IN_PROGRESS → IN_REVIEW; motivo y explicación requeridos |
| RESOLVED | ROUTED o IN_PROGRESS → RESOLVED; publicMessage y resolution.type canónico requeridos |
| REJECTED | ROUTED o IN_PROGRESS → CANCELLED según reglas; principal con duplicados activos exige revisión de alcance |

updatedBy sólo EXTERNAL_USER/SYSTEM según schema y negocio; id UUID o null según contrato.
ticketId es el UUID de M2, no un número de expediente M7. Se validan detalles, fechas,
área, estado y orden. M2 conserva autoridad sobre prioridad, clasificación, estado y SLA.
No se inventan tipos de resolución de Tránsito ni campos newStatus/previousStatus.

## Evidencias externas

Se reutilizan ExternalAttachmentService, ExternalAttachmentReference, repositorio,
controller y V51. Persistencia transaccional junto a Inbox y negocio; unicidad por
eventId/ordinal; visibilidad INTERNAL por defecto. publicMessage no convierte una
evidencia en pública. PROGRESS sólo con attachments no vacíos es válido.

No hay descarga, proxy, redirect ni binarios/storageKeys remotos ficticios. Se validan
URL absoluta HTTP(S), host, ausencia de userinfo, nombre, tipo MIME y tamaño opcional
no negativo. No hay allowlist de hosts ni verificación de accesibilidad/contenido remoto.
El endpoint de referencias usa no-store: AGENT/ADMIN, responsable del área actual;
propietario identificado sólo PUBLIC. Terceros/anónimos no acceden. Las URLs privadas
no se republican ni se guardan en el recibo sanitizado de Inbox.

Diferencia de alcance a ratificar: M2 v1.79 §12 menciona reintentar una descarga de
adjunto inaccesible; este backend sólo conserva referencias y no realiza esa descarga.
No se implementa descarga automática en este trabajo. M7 mantiene autorización y
caducidad remotas; acordar visibilidad, disponibilidad y acceso antes de homologar.

## Idempotencia y errores

| Caso | Política conservada |
| --- | --- |
| eventId/hash ya procesado o rechazo terminal | ACK sin repetir efectos |
| Colisión de eventId con contenido distinto | NACK EVENT_ID_COLLISION |
| Otra área/productor, desconocido, antiguo o estado incompatible | Recibo sanitizado y ACK; tipos ajenos se ignoran sin negocio |
| Rechazo permanente de negocio | Rollback; auditoría FAILED/REJECTED_BUSINESS_RULE en transacción nueva; ACK tras commit |
| Error transitorio, commit o auditoría fallidos | Rollback y NACK |
| PROGRESS antes de STARTED | NACK PREMATURE_PROGRESS, sin recibo definitivo; puede reprocesarse |
| Envelope/schema/versión inválidos | NACK sin efectos |

Consumer hace ACK después del retorno del proxy transaccional. Conserva
`basicNack(tag,false,false)`; la demora/retry/DLQ dependen de Core. El contrato describe
5 s → 30 s → 2 min → 10 min; default maxAttempts=4 cuenta entregas y da ventana 2 min 35 s.
No se verifica esa configuración real ni se modifica. Outbox usa su política distinta.
Se rechazan hechos anteriores al último externo o al estado local; timestamps iguales
se resuelven con reglas de estado, sin presumir orden total. No hay eventos espejo;
puede existir un hecho independiente de escalamiento al aplicar un evento externo.

## Configuración y homologación pendiente

Inbox/Outbox deshabilitados por defecto. Sólo en entorno autorizado configurar
CORE_INBOX_ENABLED/CORE_OUTBOX_ENABLED; CORE_RABBIT_HOST, puerto 5671, vhost core y
credenciales propias de M2 por configuración segura. TLS usa truststore JVM y verificación
de hostname. Declaraciones de exchange/cola son pasivas. Mantener aprobación Outbox
vigente: lista manual o autoaprobación exclusivamente con proveedor M1, simulador
apagado y lista manual vacía. No copiar secretos ni fixtures de CI a ambientes reales.

1. Obtener contrato/confirmación escrita y fixtures oficiales de M7: slug, variantes,
   transiciones, actores, nulabilidad, clasificación, evidencias y política de privacidad.
   Comparar con M2 v1.79 y registrar divergencias; no cambiar schemas unilateralmente.
2. Core debe confirmar registro/identidad, permisos, cola M7, bindings y suscripciones:
   M7 a ticketUpdated, M2 a updateTicketStatus; preservar M1/M3/M4. El DOCX §12 informa
   que la coincidencia sourceModule/identidad se valida por HTTP pero todavía no por
   AMQP; el mapeo local no prueba autenticidad. Confirmar garantías actuales con Core.
3. Consultar registro de event-types y topología/DLQ autorizados. §13.1 exige para Core
   schemas de **data autocontenidos** del paquete oficial, sin $ref externos. No cargar
   schemas completos ni modificar recursos compartidos. Confirmar owner de
   updateTicketStatus: el DOCX describe traspaso pendiente; no se acredita estado actual.
4. Con datos y permisos reales de pruebas, M2 crea/deriva a M7 y publica ROUTED.
   Guardar evidencia de Outbox/confirm y recepción efectiva M7 con el mismo UUID/eventId.
5. M7 reconoce el ticket y publica STARTED; M2 actualiza IN_PROGRESS. Probar PROGRESS
   y RESOLVED, correlación/causalidad, mensajes, SLA y evidencias sin duplicados/espejos.
6. En tickets separados probar información/respuesta, RETURNED, REJECTED, reapertura,
   cancelación, reclasificación y escalamiento. PRIORITY_CHANGED permanece reservado.
7. Core verifica confirmaciones, entrega duplicada, colisiones, hechos antiguos,
   PROGRESS prematuro y retry/DLQ reales. Reenviar eventId no recupera una entrega
   agotada: §12 describe recuperación administrativa en DLQ, con autorización operativa.
8. Registrar evidencia sanitizada de ambos módulos/Core, versiones y conformidad de
   los equipos. Sólo entonces declarar homologación bilateral.
